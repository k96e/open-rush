## 本阶段目标

建立「模型 ↔ 供应商」的集中目录，并做到**运行时增删改、不重启、不改代码即生效**（F4 / A7 / A8）。

机制：DB 唯一真相 + 进程内不可变快照 + `LISTEN/NOTIFY` 失效通知 + 轮询兜底。

## 本阶段的硬约束（既定决策，不要自行改动方向）

- **任何目录/凭据写操作都必须调 `bumpCatalogVersion(db)`**，否则副本永远看不到变更。这是最容易漏的一步——每个 POST/PATCH/DELETE 路由都要有。
- `pg_notify` **必须在事务提交后发出**，否则监听方可能读到旧数据。
- `resolveRoute` 的排序规则是 A4 的判定依据，必须确定性：`enabled` 过滤 → `priority` 升序 → 并列按 `id` 升序。
- 未知 alias 的 404 错误体**只回显被请求的 alias**，不能列出目录里其他模型名（避免枚举泄露）。

## 易踩坑

- `version` 没变时**不要去 loadSnapshot**——轮询必须是零成本的（只 SELECT 单行）。单测要断言这一点。
- `loadSnapshot` 抛错时**保留旧快照**继续服务，不要清空。DB 抖动期间网关应该按上一份目录照常工作。
- 并发 refresh 要去重（多个 NOTIFY 同时到达只跑一次）。
- 删除被 provider 引用的 credential 会撞 `onDelete:'restrict'` 的 PG 错误——要捕获并转成 v1 的 409，不能直接 500。

## 阶段完成判定

#### T3.1 `CatalogStore` + Drizzle 实现
- **产出**：`src/catalog/types.ts`、`catalog-store.ts`（interface）、`drizzle-catalog-store.ts`
- **要点**：`loadSnapshot()` 一次性 join 出 providers + models + credentials，**在内存里按 `(alias) → 排序后的候选数组`** 建索引（排序规则见 C3 §7.7），使 `resolveRoute` 为 O(1)
- **验收**：PGlite 测试覆盖：只加载 enabled 行、priority 排序、并列按 id、provider disabled 时其 model 不进索引
- **依赖**：T1.1

#### T3.2 `CatalogCache` ⇉
- **产出**：`src/catalog/catalog-cache.ts`（见 C3 §7.6）、`bump-version.ts`
- **验收**：用 fake store + fake listener 测：boot 加载、version 未变时**不调用 loadSnapshot**、NOTIFY 触发刷新、并发 refresh 去重、loadSnapshot 抛错时保留旧快照、`stop()` 清理定时器
- **依赖**：T3.1, T1.2

#### T3.3 `resolveRoute` ⇉
- **产出**：`src/catalog/resolve-route.ts`（见 C3 §7.7）
- **验收**：命中 / 未知 alias / 全部 disabled / 多候选取最小 priority / mode 判定（同名→passthrough，异名→rewrite-model）
- **依赖**：T3.1

#### T3.4 providers / models 控制台 API
- **产出**：`apps/web/app/api/v1/llm/providers/**`、`models/**`
- **要点**：每次写操作后 `bumpCatalogVersion`；删除被引用的 credential 返回 409（`onDelete:'restrict'` 的 PG 错误要捕获并转成 v1 信封）
- **验收**：每个 method 的正常 + 错误 + 权限拒绝
- **依赖**：T1.1, T0.2
