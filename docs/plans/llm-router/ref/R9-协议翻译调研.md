## 9.1 要解决的到底是什么问题

D2 把 `translate` 定义成「调用方协议 != 上游协议」，落到实际部署里只有一个场景：

```
Claude Code ──Anthropic Messages──▶ [llm-router] ──OpenAI Chat Completions──▶ 任意兼容供应商
```

反方向（我们自己的服务用 OpenAI SDK 打 Anthropic 上游）**目前没有需求**，本次不交付
（`selectTranslator` 对它返回 null，路由层维持 404 + `PROTOCOL_FACE_MISMATCH`）。

难点不在字段改名，而在三处**结构性不对称**：

| # | 不对称 | 后果 |
|---|---|---|
| ① | Anthropic 的 `system` 是顶层字段，OpenAI 的 system 是 `messages[0]` | 必须重排消息数组，Claude Code 的归属块剥离逻辑因此失效（§9.4·坑④） |
| ② | Anthropic 的 `tool_result` 挂在 **user** 消息的内容块里，OpenAI 要求独立的 `role:'tool'` 消息 | 一条 Anthropic 消息可能要拆成 N+1 条 OpenAI 消息，且顺序有硬约束 |
| ③ | Anthropic 流一次只能开一个 content block 且**关掉就回不去**，OpenAI 的 `tool_calls[].index` 允许交错 | 逐片直发的写法在并行工具调用上会静默丢参数（§9.4·坑②） |

## 9.2 现有方案横向对比

调研于 2026-09，只看**真的在生产里跑 Claude Code 的**实现，不看纯 SDK 转换库。

| 方案 | 形态 | 流式 | 工具调用 | 思考内容 | 值得抄的 | 值得躲的 |
|---|---|---|---|---|---|---|
| **LiteLLM** `anthropic_adapter` / `experimental_pass_through` | Python 代理，功能最全 | ✅ | 逐片直发 `input_json_delta` | 只认 `thinking_blocks` | `finish_reason` 映射表、tool 名 64 字符截断+哈希还原、`prompt_tokens - cache` 的 usage 口径 | **`reasoning_content` 被整段丢掉**（issue #29518）——vLLM / SGLang / DeepSeek 系上游的思考过程在 Anthropic 侧完全消失 |
| **APISIX / API7 `ai-proxy`** | 网关插件，声明式配置 | ✅ | 有 | 无 | 「协议转换是网关的职责而不是应用的职责」这条定位 | 映射写死在插件里，扩展要改 Lua |
| **anthropic-proxy**（FightAloneDC） | Node 单进程代理 | ✅ | 有 | 有：`reasoning` → `thinking`，还做 `<think>` 标签归一化 | `metadata.user_id → user`、`thinking.budget_tokens → reasoning_effort`、缓存 token 双向映射 | 标签归一化是**猜测式**改写，会误伤正文里合法出现的 `<think>` |
| **a4f-proxy** | Cloudflare Worker，双向 | ✅ | 有 | — | 本地 token 计数兜住 `count_tokens` | Worker 环境下没法做旁路计量，与我们的 A5 目标不同源 |
| **官方 Claude Code gateway 文档** | 规范而非实现 | — | — | — | **三条硬要求**（§9.3），这是所有实现里唯一权威的一份 | — |

一句话结论：**映射本身是共识，坑都在流式与「翻译改变了 Claude Code 的假设」这两处。**

## 9.3 官方文档给出的三条硬要求（照做，不讨价还价）

来自 Claude Code 的 gateway 兼容性指南（`code.claude.com/docs/en/llm-gateway-protocol`）：

1. **翻译过来的流必须自己发 `ping`。**
   > "An upstream that sends no pings at all … leaves those pauses with nothing to forward.
   > **When translating from such an upstream, emit your own `ping` events during silent gaps.**"

   `ANTHROPIC_BASE_URL` 连接上有 **300 秒字节级看门狗**，而 OpenAI 兼容上游一个 ping 都不发。
   长思考、长工具参数生成期间不补心跳 = 流被客户端判死。
   → 落点：`adapters/translate-stream.ts`，空闲触发，默认 15s（`LLM_ROUTER_TRANSLATE_PING_MS`）。

2. **上游错误体一个字节都不能动。**
   > "The retry logic matches on the upstream's error wording, so forward error response bodies
   > unmodified. A gateway that wraps upstream errors in its own envelope breaks the recovery path,
   > **even when it preserves the status code**."

   → 落点：`forward.ts` 里 `translating = translator !== undefined && upstream.status < 400`。
   **翻译只对 2xx 生效**。代价是 Anthropic 面的调用方在出错时会拿到一份 OpenAI 形状的错误体——
   两种形状都有 `error.message`，Claude Code 的文案匹配照常工作，这是刻意选的那一边。

3. **跨协议时「开放列表」原则要反过来。**
   > "Treat the headers and body fields as open lists, not closed ones. …
   > **The exception is a non-Anthropic upstream** …, where bridging the schema difference is the
   > gateway's job."

   → 落点：`anthropic-to-openai.ts` 用**封闭 allowlist**，`headers.ts` 的 `crossProtocol` 剥掉
   所有 `anthropic-*`。理由很实在：Claude Code 对**不认识的模型名**（网关 alias 正是）会照发
   `thinking: {"type":"adaptive"}`、`context_management`、`output_config`，这些送给 OpenAI 上游
   只会换来 `400 Extra inputs are not permitted`。

## 9.4 五个坑（前四个是别人踩出来的）

**① `reasoning_content` 被丢掉**（LiteLLM issue #29518）
适配器只认 Anthropic 官方的 `thinking_blocks`，而 vLLM / SGLang / DeepSeek 系上游填的是
`reasoning_content`。结果是正文还在、思考全没。
→ 我们的做法：`delta.reasoning_content ?? delta.reasoning` 都认，翻成 `thinking` 块。
`signature` 留空字符串——那段思考不是 Anthropic 签的，**不伪造签名**。

**② 并行工具调用交错时丢参数**
OpenAI 的 `tool_calls[].index` 允许 `0 → 1 → 0 → 1` 这样交错回；Anthropic 的块一旦
`content_block_stop` 就回不去。逐片直发的实现会把回到已关闭块上的参数片段直接丢掉。
→ 我们的做法：**按 index 攒齐，`end()` 时按 index 升序整块发出**。
代价只是工具参数不再逐字流出——而 Claude Code 本来就要等 `message_stop` 之后才执行工具，
且经网关时「细粒度工具流式」默认是关的，功能上零损失。

**③ 上游回了 `tool_calls` 却把 `finish_reason` 写成 `stop`**
不少兼容实现如此。照抄过去，Anthropic 侧的调用方会以为这轮是普通结束，**根本不去执行工具**。
→ 我们的做法：`mapFinishReason(reason, sawToolUse)` —— 出现过 tool_use 且映射结果是
`end_turn` 时改判 `tool_use`；`length` 不改（那是真被截断了）。

**④ 系统提示归属块**
Claude Code 在 `system` 数组首位放一段归属块，`api.anthropic.com` 会**按位置**剥掉它。
翻译必然重排 `system`（结构性不对称①），剥离逻辑因此失效，那段文本会进入上游的提示词与缓存键。
→ 我们的做法：无法在网关侧解决（官方明说要在客户端关），因此**写进上线手册**：
走 translate 的部署应同时设 `CLAUDE_CODE_ATTRIBUTION_HEADER=0`。

**⑤ 流式没有 usage**
OpenAI 兼容协议下不带 `stream_options.include_usage=true` 就一条 usage 都不回，A5 直接落空。
→ 我们的做法：翻译时**总是**写上（反正整个 body 都是重建的，这不是额外的改写）。

## 9.5 映射契约

### 9.5.1 请求：Anthropic Messages → OpenAI Chat Completions

| Anthropic | OpenAI | 备注 |
|---|---|---|
| `model` | `model` | 换成目录里的 `upstream_model` |
| `system`（string / 文本块数组） | `messages[0] = {role:'system'}` | 文本块用 `\n\n` 拼接；非文本块丢弃 |
| `messages[].content` = string | `{role, content}` | 原样 |
| user · `text` 块 | `content` 字符串（纯文本时）或 `[{type:'text'}]`（含图片时） | 纯文本降级成字符串——不少兼容实现只认字符串 |
| user · `image` 块 | `[{type:'image_url', image_url:{url}}]` | `base64` → data URI；`url` → 原样 |
| user · `tool_result` 块 | **独立的** `{role:'tool', tool_call_id, content}` | **排在同轮普通内容之前**（OpenAI 的顺序硬约束） |
| assistant · `text` 块 | `content`（多块拼接） | 只有 tool_use 时 `content: null` |
| assistant · `tool_use` 块 | `tool_calls[]`，`input` → `JSON.stringify` | |
| `tools[]`（有 `input_schema`） | `tools[] = {type:'function', function:{name, description, parameters}}` | 一个都不剩时不发 `tools` 字段 |
| `tool_choice` `auto`/`any`/`none`/`tool` | `'auto'`/`'required'`/`'none'`/`{type:'function',...}` | 没有 tools 时不发 |
| `max_tokens` / `temperature` / `top_p` | 同名 | `max_tokens` 而不是 `max_completion_tokens`——兼容实现的最大公约数 |
| `stop_sequences` | `stop` | |
| `stream` | `stream` + `stream_options.include_usage=true` | 见坑⑤ |
| `metadata.user_id` | `user` | |

**刻意丢弃**（留着就是上游 400 或非法结构）：
`top_k`、`thinking`、`context_management`、`output_config`、`mcp_servers`、`container`、
`anthropic_version`、所有 `cache_control` 标记、`thinking` / `redacted_thinking` / `document` /
`tool_reference` 内容块、Anthropic 托管工具（无 `input_schema` 的）。

**请求头**：跨协议时额外剥掉所有 `anthropic-*`（见 §9.3·3）。凭据仍按 `authStyle` 注入。

### 9.5.2 响应（非流式）：OpenAI → Anthropic

| OpenAI | Anthropic |
|---|---|
| `id` | `id`（缺失时造 `msg_<32hex>`；有就原样沿用，两侧日志能对上） |
| `model` | `model`（缺失时用目录里的 `upstream_model`） |
| `choices[0].message.reasoning_content` / `.reasoning` | `content[] += {type:'thinking', thinking}` |
| `.content` / `.refusal` | `content[] += {type:'text', text}` |
| `.tool_calls[]` | `content[] += {type:'tool_use', id, name, input}`（`arguments` 解析失败 → `{}`） |
| `finish_reason` | `stop_reason`（见 §9.5.4） |
| — | `stop_sequence: null`（OpenAI 不说命中的是哪条） |
| `usage` | 见 §9.5.5 |

**翻不动就回 null**（非 JSON / 没有 `choices`）→ `forward()` 回 502 + `UPSTREAM_UNTRANSLATABLE`，
错误体只含供应商 `name`。宁可 502，也不把上游形状的 body 冒充成 Anthropic 响应。

### 9.5.3 响应（流式）：OpenAI chunk → Anthropic 事件序列

```
第一个 chunk        → event: message_start      （usage 全 0，见「有损清单」）
delta.reasoning_*   → content_block_start(thinking) + content_block_delta(thinking_delta)
delta.content       → content_block_start(text)     + content_block_delta(text_delta)
   （换 kind 时先 content_block_stop 上一个块）
delta.tool_calls[]  → 只累积，不发事件
流结束              → content_block_stop（关掉在开的块）
                    → 每个工具按 index 升序：content_block_start(tool_use)
                                          + content_block_delta(input_json_delta)
                                          + content_block_stop
                    → message_delta（stop_reason + 完整 usage）
                    → message_stop
空闲 ≥ ping 间隔    → event: ping（任意时刻插入）
```

上游一个 chunk 都没回时，仍然发出 `message_start → message_delta → message_stop`
的完整空消息——客户端不该永远等下去。

### 9.5.4 `finish_reason` → `stop_reason`

| OpenAI | Anthropic |
|---|---|
| `stop` | `end_turn` |
| `length` | `max_tokens` |
| `tool_calls` / `function_call` | `tool_use` |
| `content_filter` | `refusal` |
| 其他 / 缺失 | `end_turn` |

**修正项**：出现过 tool_use 且映射结果为 `end_turn` 时改判 `tool_use`（坑③）。

### 9.5.5 usage

```
input_tokens                = prompt_tokens - prompt_tokens_details.cached_tokens
cache_read_input_tokens     = prompt_tokens_details.cached_tokens
cache_creation_input_tokens = 0        ← OpenAI 面没有这个维度
output_tokens               = completion_tokens
```

与 `usage/openai-parser.ts` **完全同口径**——同一份账不能有两种算法。
注意计量走的是**上游原始字节**（tee 在翻译之前），翻译产物不参与记账。

## 9.6 有损清单（验收报告的 F2 / A1 栏必须原样抄过去）

`translate` 档**不承诺字节一致**，只承诺语义等价。以下是明知的、可接受的损失：

| # | 损失 | 影响 | 为什么接受 |
|---|---|---|---|
| 1 | `message_start.usage` 全 0 | 客户端在开头看不到输入 token 数 | OpenAI 到最后一个 chunk 才给 usage；真实值在 `message_delta.usage` 里给全 |
| 2 | `stop_sequence` 恒为 null | 客户端不知道命中的是哪条停止串 | OpenAI 协议里没有这个信息 |
| 3 | 工具参数不逐字流出 | 无（Claude Code 等 `message_stop` 后才执行工具） | 换来并行工具调用不丢参数（坑②） |
| 4 | `thinking` 块没有 signature | 不能把这段思考回传给真 Anthropic 上游 | 不伪造签名 |
| 5 | 上一轮的 `thinking` / `document` 块被丢 | 多轮对话里模型看不到自己上一轮的思考过程 | OpenAI 消息结构里没有它们的位置 |
| 6 | `tool_result` 里的图片被丢 | 工具返回截图时模型只看得到文字部分 | OpenAI 的 `role:'tool'` 消息只收文本 |
| 7 | `top_k` / `cache_control` / 各类 Anthropic 专有字段被丢 | 提示缓存在上游侧不生效 | 不丢就是 400 |
| 8 | 归属块进入上游提示词与缓存键 | 上游侧缓存命中率下降 | 网关侧无解，靠 `CLAUDE_CODE_ATTRIBUTION_HEADER=0`（坑④） |
| 9 | 出错时调用方拿到 OpenAI 形状的错误体 | Anthropic SDK 仍读得到 `error.message` | 官方明令上游错误体不得改写（§9.3·2） |
| 10 | `count_tokens` 跨协议时回 404 | Claude Code 退化成用推理请求估算上下文 | OpenAI 侧没有对应端点；这是官方支持的降级路径 |

## 9.7 退路

翻译层出问题时**不需要回滚镜像**：设 `LLM_ROUTER_TRANSLATE_ENABLED=false`，
跨协议立刻退回 M4 的行为（404 + `PROTOCOL_FACE_MISMATCH`）。
同协议的 `passthrough` / `rewrite-model` 两档一个字节都不经过这一层，不受影响。
