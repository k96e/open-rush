## 一、这是什么

给 `kanyun-rush/open-rush` 加一层**极薄的统一模型路由网关**（`llm-router`）：所有 LLM 调用收敛到这一层，对外呈现统一的、供应商无关的模型入口，同时接上密钥收敛、逐调用计量、预算与限流。

**调研基线**：`e62f507c37603cb7df40d87b5b4ee94a285503c7`（2026-04-28，`main` 的 HEAD）。
开工前跑一次 [`ref/R0-基线与复现.md`](ref/R0-基线与复现.md) §1.3 的差异复核（15 分钟）。

## 二、架构落位（一句话记住）

```
control-worker ──SSE①── agent-worker ── Claude Code CLI ──▶ [ llm-router ] ──▶ 供应商
                                          ↑ ANTHROPIC_BASE_URL 指到这里
```

**网关夹在 Claude Code CLI 与供应商之间，不是夹在 control-worker 与 agent-worker 之间。**

这条选择带来三个后果，是整个方案的地基：

1. **双层 SSE 与 15 状态机一个字节都不经过网关** → A1（透传语义）、A3（可用性）天然成立。
2. 接入方式就是 Claude Code 官方的 gateway 协议（`ANTHROPIC_BASE_URL` + `ANTHROPIC_AUTH_TOKEN`）→ 不需要发明私有协议。
3. 沙箱里拿到的是**网关签发的短时令牌**，不是供应商真 key → 即使 agent 有 bash 也偷不到东西。

## 三、12 条决策（一行一条，理由见 `ref/R2`）

| # | 结论 |
|---|---|
| D1 | 独立服务 `apps/llm-router`（Hono，:8790），夹在 Claude Code CLI ↔ 供应商之间 |
| D2 | 对外同时暴露 Anthropic Messages 与 OpenAI 两个协议面；上游适配分 `passthrough` / `translate` |
| D2b | 默认 `alias == upstream_model` → 字节级零改写；异名时只允许改 `$.model` 一个字段 |
| D3 | 密钥用**非对称信封**（X25519 sealed box）：web 只有公钥，llm-router 独占私钥 |
| D4 | 与既有 Vault **并存不耦合**，不改造 Vault |
| D5 | 调用方凭据用新表 `llm_router_tokens`，per-run 短时令牌；复用 `service_tokens` 的范式不复用表 |
| D6 | **令牌即归属**；`x-claude-code-session-id` 等 header 只作分组提示，不作授权与计费依据 |
| D7 | 热变更 = DB 唯一真相 + 进程内快照 + `LISTEN/NOTIFY` + 轮询兜底（默认 5s） |
| D8 | 逐调用写 `llm_calls`（异步批写、失败不阻塞）；run 收敛时聚合回写 `data-openrush-usage` |
| D9 | 限流复用 `RedisRateLimiter`；预算用 DB 累计器，`observe` / `enforce` 两档 |
| D10 | 三套错误信封：上游错误**原样透传** / 网关错误按调用方协议成形 / 控制台用 v1 信封 |
| D11 | 无状态多副本；`readyz` 摘流 + 优雅 drain |
| D12 | 不依赖沙箱网络策略——**没有钥匙就没有门** |

## 四、绝对边界（不可违反）

**不做**：
- ❌ 不改写请求/响应语义（不做提示词加工）
- ❌ 不改 agent-worker 与 Claude Code 的既有调用语义（只换 `ANTHROPIC_BASE_URL` 指向）
- ❌ 不改双层 SSE 协议、不改 15 状态机、不改 `run_events` 既有事件类型
- ❌ 不重构 `packages/agent-runtime`（它是死代码，只复用其中的 `RedisRateLimiter`）
- ❌ 不改造既有 Vault
- ❌ 不接现网

**必须**：
- ✅ 供应商真 key 只在 llm-router 进程内存出现，其余任何位置（web / control-worker / agent-worker / 沙箱 env / DB / 日志 / 响应）都不得有明文
- ✅ 计量失败不阻塞上层调用
- ✅ 请求头走**开放列表**转发，不做白名单过滤
- ✅ 上游错误体**原样透传**，不包信封
- ✅ `llmAccess` 是可选依赖——不装配时行为与改造前完全一致

## 五、三个最容易踩的坑

**① dev 模式下 env 有两条路径，只改一条会以为网关没生效**
`LocalDevSandboxProvider.create()` 完全忽略 `options`。必须**同时**把 env 传给 `agentBridge.sendPrompt`，并清空 `apps/agent-worker/.env.local` 里的 `ANTHROPIC_BASE_URL` / `ANTHROPIC_API_KEY`。
→ 详见 [`ref/R3-架构与数据流.md`](ref/R3-架构与数据流.md) §4.2.1

**② provider 升级会把密钥重新泄漏进沙箱**
锁定的 `ai-sdk-provider-claude-code@3.4.4` 子进程 env 白名单**不含** `ANTHROPIC_*`；3.6.0+ 新增了前缀继承。所以要**显式置 `undefined`**，不能靠"不设置就没有"。
→ 详见 [`ref/R1-现状盘点.md`](ref/R1-现状盘点.md) §2.8

**③ 目录写操作忘了 bump version，副本永远看不到变更**
每个 POST/PATCH/DELETE 路由都要调 `bumpCatalogVersion(db)`，且 `pg_notify` 必须在事务提交后发。

## 六、仓库现状的 3 条反直觉事实

课题说明写于更早的状态，与基线有 8 处偏差（全部见 `ref/R1`）。这三条会直接影响你的判断：

1. **`packages/agent-runtime` 是死代码**——全仓零 import。模型配置的真实落点是 `apps/agent-worker/src/server.ts:102-125`。
2. **`data-openrush-usage` 从未被任何代码发出**，只有 zod schema 和文档。所以 F5 是从零到有，不是升级。
3. **Vault 完全没接线**（`resolveVaultEnv: async () => ({})`），密钥其实来自 agent-worker 自己的 `process.env`。

## 七、提交门禁（`AGENTS.md` 铁律，无例外）

```
1. pnpm build   → 失败则修
2. pnpm check   → 类型错误则修
3. pnpm lint    → 用 pnpm format 修
4. pnpm test    → 失败则修
5. Sparring Review → MUST-FIX 清零
```

外加两条硬要求：
- **代码 + 测试必须在同一个 commit**，不允许"先提代码后补测试"
- 每个 API route / service 方法 / utils 函数都要有单测，覆盖正常路径 + 至少一个错误路径
